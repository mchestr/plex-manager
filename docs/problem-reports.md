# Problem reports

Members report a problem with a title (a copy that won't play, a bad picture, the wrong movie, missing episodes) from `/report`, and follow what happens to it. Missing episodes are looked for on their own, a better copy of a blurry movie or episode when the quality profile wants one, and wrong details are read again once the title is checked against Radarr or Sonarr (see Fixes). Once the server admin turns members' swaps on, members can also swap a copy that won't play right and fix a Plex match themselves, within limits (see Members' swaps). Every other report goes to the server admin, who can run a fix from the report in one tap, such as swapping a bad copy for another release or fixing the Plex match.

The feature is off until the switch is on (`ProblemReportSettings.enabled`, off by default), in the settings card at the bottom of **Automations > Problem reports**. While it is off, Help and Home don't link to `/report`, and the page shows only Your reports, to a member who made or follows one, who can still cancel theirs; for anyone else it is a 404. The server admin keeps every report, and reports stay in each member's Your data.

## For members

- **Entry points:** Help, Report a problem links to `/report`, and the Home help card has a Report a problem row. The Discord links stay. There is no top-bar item.
- **The page**, top to bottom: **Watching now** (the member's own Plex streams, shown only while they stream), **Find a title** (a `?q=` search), **Recently watched** (their Tautulli history, newest first, one row per movie and one per show at its newest episode) and **Your reports**. Every list holds only movies, shows and episodes in libraries shared with the member. When Plex or Tautulli can't be read, its list says so and the rest of the page still loads.
- **The sheet:** a title opens a bottom sheet (`/report?item=<ratingKey>`, so a link can open it directly).
  - Step 1 asks what kind of problem, one full-width row per kind. Episode problems appear only for shows and episodes.
  - Step 2 asks which problem, the episode for a show, and an optional note (required for "Something else"). The line under it and the button say what happens (`lib/problem-reports/consequence.ts`, the same words in Discord): **Send to the server admin**; **Look for them** for "Episodes are missing" when Sonarr is set up ("We'll check which episodes are missing and look for them. Nothing is removed."); **Look for a better copy** for "Blurry or low quality" about a movie when Radarr is set up, or an episode when Sonarr is ("We'll look for a better copy. If there isn't one, nothing changes."); or **Fix the details** for "The title, poster or description is wrong" about a movie when Radarr is set up, or a show or an episode when Sonarr is ("We'll check the details and ask Plex to read them again. The file stays the same."). The report checks again when it is sent, and the fix checks before it acts, so these lines never promise more than a look.
  - While members' swaps are On, a problem a swap fixes shows **Swap the copy** ("We'll find a different copy and swap it in. The one you have keeps playing until the new one is ready, which can take a few minutes to a day. Uses 1 of your 3 swaps.") with the member's allowance under it ("2 of 3 swaps left. One comes back Nov 10."), and "A different movie or episode plays" shows **Fix the details** ("We'll fix the title and poster in Plex. The file stays the same."). When a limit refuses the swap, the button sends the report to the server admin and the line under it says why ("You're out of swaps until Nov 10."). See Members' swaps. In Dry run and Off, the sheet says the server admin's words.
  - "Episodes are missing" can end in an answer instead of a report: "Season 2, episode 6 comes out Nov 14." when the missing episodes haven't aired, or "Season 3 isn't on the server." with **Request it** (the show's Overseerr page) when they aren't monitored. When Look for the episodes starts, the sheet says "We'll look for the missing episodes now. Nothing is removed."
  - For a playback problem that may be the device (won't start, stops, glitches, out of sync, no sound), when Tautulli knows the member's last player of the title, it asks "Does anything else play on Living Room?": **Yes, others play fine**, **No, nothing plays** or **I haven't tried**. The last two show playback tips. For a show, the question is about the show's last play, so it goes away when the member picks one episode.
  - "Blurry or low quality" can end in an answer too: "This is the best copy the server keeps." when the quality profile wants nothing better, with **Send to the server admin** for a member who still wants it looked at. When Look for a better copy starts, the sheet says "We'll look for a better copy now. The one you have keeps playing, and if there isn't a better one, nothing changes."
  - For a blurry or glitching picture after a play that Plex converted, it first says "Your Plex app converted this video while you watched, which lowers quality and can cause buffering." with a link to the playback guide. A blurry picture then goes to the server admin, with "Still blurry with the quality set to Maximum? Send it to the server admin.": a converted play is soft whatever the file. For a show, the tip is about the show's last play, so it goes away when the member picks one episode.
  - Back returns to step 1, and focus moves to each step's heading.
- **Already reported:** a title has at most one open report. The sheet then says "This title already has an open report: Sound is out of sync. With the server admin since Nov 6." with **Same problem, tell me when it's fixed** (follow it) and **It's something else** (report another problem, which is added to the open report for the server admin).
- **Your reports:** the member's reports and the ones they follow, with the status, the latest step and **Cancel report** while nothing has run on it (`lib/member/your-reports.ts`). While a fix runs, the status says what it is doing ("Looking for the episodes", "Looking for a better copy"); a member's swap in Dry run reads as With the server admin instead (`lib/member/dry-runs.ts`), since that is what the member was told. Once the server admin marks a report fixed or closes it, the member who reported it sees the admin's note there, as plain text. Followers see the status only, since the note is written to the reporter.
- **No better copy right now:** a member's Look for a better copy that finds nothing closes their report with that reason. The member who reported it gets **Ask the server admin** on it, once: the report goes back to the server admin and the admins get the usual alert. When the title has another open report by then, their problem joins that one (`lib/problem-reports/ask-admin.ts`).
- **Does it play now?:** after Swap the copy or Remove the file and search fixes a report, from any trigger, the member who reported it gets **It plays** and **Still broken** on it, once, for 7 days. It plays goes on the timeline. Still broken asks "What's still wrong?" and puts the report back with the server admin with their answer, and the admins get the usual alert; it never starts another swap, and when the title has another open report by then, their problem joins that one, and their own report stays fixed with the answer on its timeline. With no answer in 7 days the question goes away, and the report stays fixed. Followers aren't asked.
- **DMs:** when a report is fixed or closed, the member who made it and each follower with a linked Discord get a text DM with a link to `/report` (`PROBLEM_REPORT_UPDATE`, `lib/queue/jobs/problem-report-update.ts`), one per change, between 09:00 and 20:00 in their zone (the server's when they have none). A fix says what it did ("A better copy of Heat (1995) is on the server now.", "A different copy of Heat (1995) is on the server now." after a swap, to which the member who reported it reads "Does it play? Tell us on your reports."), and a search that found nothing says so, telling the member who reported it that they can ask the server admin. A member who cancels gets none; their followers do. Closed DMs (50007) are not retried.

## In Discord

`/report title:<name>` reports a problem from Discord (`lib/discord/commands/report/`). Every reply is ephemeral.

- The member must be linked and have an active membership, and the switch must be on. The search shows only movies, shows and episodes in the member's libraries (`lib/problem-reports/search.ts`, shared with the web's Find a title). There is no autocomplete: the router checks no user for one, and the library check would not fit in its 3 seconds.
- The steps match the web sheet: which title, what kind, which problem, then the confirm with the web's line and button (and its playback tip after a converted play), which goes through the same service as the web. An answer that the file is the best copy the server keeps comes with **Send to the server admin**. A show hands off to `/report?item=<ratingKey>` to choose the episode, and "Something else" hands off to the web for its note. Discord doesn't ask the device question, so a playback problem goes to the server admin there; while members' swaps are On, a copy filmed off a screen or with subtitles stuck on gets **Swap the copy** with the allowance, as on the web.
- Each control's `custom_id` carries what the next step needs (`lib/discord/commands/report/ids.ts`), so nothing is stored between steps. Every step checks the member again and reads the title from Plex again, against their libraries.
- `/watching` puts a **Report a problem** button on each movie or episode stream while the switch is on. The button carries the member's Discord id and the stream's rating key, and anyone else who presses it is told it belongs to someone else.
- `/report` replaced `/mark badquality`. Earlier poor-quality marks stay, and `/mymarks type:badquality` still lists them. After an upgrade that adds or changes commands, run `npm run register-discord-commands` (`node scripts/dist/register-discord-commands.cjs` in the image) so Discord shows them.

## For the server admin

- **Automations > Problem reports** is the first Automations tab, so the item and the phone tab bar open on it. The Automations badge says "N to review" for reports with the server admin; failed jobs keep priority.
- **The list** (`?status=`): Needs you (oldest first), Fixing, Fixed and Closed (newest first), each with its count. A row shows the title, the problem, who reported it (+N for the other members who reported or follow it), the status and when.
- **A report** (`/admin/problem-reports/<id>`): the title, the problem, the reporter and their note, a link to the title in the Plex web app, and the timeline: each step, who took it, a second member's problem and note, the answer about their player, and what Tautulli said when they reported it. Members' words are plain text, never Markdown.
- **Fixes:** an open report that no fix is running on offers the fix its problem points to as a button ("Swap the copy" for a copy that won't start, "Look for the episodes" for missing episodes, "Look for a better copy" for a blurry picture, "Fix the Plex match" when a different title plays, "Refresh the details" for wrong details), and the others for the title under **Other fixes**. **Remove the file and search** is there too, for a movie or an episode, and asks to confirm first (see below). A fix answers at once and runs in the job queue; the report says what it is doing, and its timeline how it went. Fixes need Redis.
- **Mark fixed** and **Close with a note** end an open report once (a second press is refused). Each takes a note the member who reported it sees on `/report` and an internal note only admins see. Ending a report frees the title for a new one, and stops a fix running on it.
- **The breaker:** when fixes that replace a file (Swap the copy, Remove the file and search) pass 5 an hour or 15 a day, from any trigger, they stop until an admin presses **Resume fixes** on the banner above the list. Admins with a linked Discord get a DM when it trips (see Discord alerts).
- **Swaps need approval** is a switch on a member's admin page (`User.swapsNeedApproval`). It sends that member's own swaps to the server admin instead of running them (see Members' swaps).
- **The settings card**, below the list, has the switch and members' swaps (Off, Dry run or On) with their limits. It waits for Radarr's and Sonarr's recycle bins, which On needs, so a slow service holds up only the card.

### Discord alerts

When the bot is on, a new report sends a text DM to every admin who linked Discord (`PROBLEM_REPORT_NOTIFY`, `lib/queue/jobs/problem-report-notify.ts`): the member, the title, the problem and a link to the report. A member's reports reach the admins at most once an hour: the first at once, and any in the next hour in one message when it ends (at most five listed, then a count). The job claims the reports (`ProblemReport.alertedAt`) before it sends, so two jobs never send the same report; an admin whose DMs are closed (Discord's 50007) is skipped without a retry, and a send that reached no admin for another reason releases the claim for a retry. An admin gets each alert at most once: when one admin's DM fails and another's goes out, the claim stays, so the first is not sent it again. A worker that stops between the claim and the sends loses that alert; the badge still counts the reports. The member's name and the titles go through `plainDiscordText` (`lib/discord/plain-text.ts`): no formatting, masked or bare links, mentions, bidi or zero-width characters, and messages go out with no allowed mentions. A join adds to a report the admins already know of, so it sends nothing. Without Redis there are no alerts; the badge still counts every report.

When the breaker trips, the same admins get one DM saying that fixes that replace files are paused, with a link to the page where they resume them (`PROBLEM_BREAKER_ALERT`, `lib/queue/jobs/problem-breaker-alert.ts`, one job per trip). It is skipped once an admin has resumed them, and closed DMs are skipped as for the report alerts.

### Fixes

`lib/problem-reports/run.ts` runs every fix as one `PROBLEM_REPORT_FIX` job (`lib/queue/jobs/problem-report-fix.ts`), whoever starts it: the app for a member's report (`automatic`), an admin on the web (`web`) or an MCP client (`mcp`).

- **Starting** claims the report: a conditional update moves an open report that no fix is running from Sent or With the server admin to Fixing, bumps `ProblemReport.runToken` and records the fix in `ProblemReport.action`. A second start, a double tap or an MCP call at the same time finds nothing to claim. The job id is the report and the run token (kept 24 hours), so a repeated enqueue adds nothing. The job's data holds when the report was claimed (`claimedAt`), which the gates check (see "Checked again before a grab or a delete"). Without Redis, or with the queue down, the report goes straight back to the server admin.
- **Each step** reads the report again and stops when the run token isn't its own or the report isn't Fixing (someone marked it fixed or closed it). With problem reports turned off, a run goes back to the server admin at its first step, before it acts; a run past it (waiting on an import or a search, or a removal about to search for the file it deleted) keeps going, so what it started is seen through. To wait, the job saves the next step in its data and delays itself, which uses no attempt.
- **The gate:** before a step acts on Radarr, Sonarr or Plex, one serializable transaction reads the ledger, checks the limits (`lib/problem-reports/fixes.ts`), adds the run's ledger row and writes `PROBLEM_FIX_RUN`. The row's id is the report and the run token, so a step that runs again after a crash finds it and doesn't act twice. Searches stop at 30 a day across every fix and trigger, and matches and refreshes of Plex items at 20 an hour; past either, reports go to the server admin. A swap's or a removal's interactive or indexer search counts as a search. The breaker counts a row once it has `replacedAt`: a removal's row has it from the start, since it deletes at once, and a swap's gets it from a second serializable gate (`gateReplace`) right before the grab. A swap's gates, and a removal's, also check again what let it start (see "Checked again before a grab or a delete").
- **Look for the episodes** reads the show's episodes from Sonarr and Plex again (`lib/problem-reports/missing.ts`). Files Sonarr has and Plex lacks (compared by file name) get a scan of the show's folder in Plex; monitored episodes that aired with no file get Sonarr's `EpisodeSearch` for exactly those episodes, which removes nothing (at most 50; more go to the server admin). It then checks every 10 minutes (2 after a scan): the report is fixed once none of those episodes are missing, scanned once more if Sonarr found files Plex lacks, and handed back after a day without them, or 30 minutes after a scan Plex didn't take.
- **Look for a better copy** (`lib/problem-reports/steps/better-copy.ts`) first resolves the file again: the one Plex plays, matched to Radarr's movie file or a Sonarr episode file (see "The file a fix acts on"). The quality profile must allow upgrades, and the file must be below its quality cutoff or below its custom format cutoff (`lib/problem-reports/upgrade.ts`): the quality cutoff alone misses a file at the right resolution from a worse release. It then sends Radarr's `MoviesSearch` or Sonarr's `EpisodeSearch` for the file's episodes with the file in place, so only an upgrade is grabbed and the old copy plays until the new one imports. The search counts against the daily cap, not as a file replacement. Every 10 minutes it reads the file, the queue and the history since the search (from a minute before it, in case Radarr's or Sonarr's clock is a little behind):
  - a new file is the better copy: Plex is asked to scan the file's folder, and the report is fixed;
  - a download the queue shows as stuck (import blocked or failed), or a failed download in the history, goes to the server admin;
  - a copy that is downloading, or was just grabbed, is waited for until a day after the search, then goes to the server admin;
  - a search that finished and grabbed nothing is "No better copy right now": a member's run closes the report (see Your reports), and an admin's run goes back to them. A search Radarr or Sonarr no longer knows (after a restart) counts as finished, and one that failed or ran for a day goes to the server admin. A step that runs again after a crash never searches twice, and has no search to ask about, so a crash between recording the run and sending the search ends as no better copy.
- **Swap the copy** (an admin's tap, or a member's own while members' swaps are On, `lib/problem-reports/steps/swap.ts`) grabs another release of the same quality or better, so the copy members have keeps playing until the new one imports. See "Swap the copy" below.
- **Remove the file and search** (admins only, behind a confirm, `lib/problem-reports/steps/remove-and-search.ts`) deletes the file and searches for any copy the quality profile allows, for when the only other copies are lower quality. See "Remove the file and search" below.
- **Fix the Plex match** (an admin's tap, or a member's report while members' swaps are On, `lib/problem-reports/steps/fix-match.ts`) matches the movie or show to the title Radarr or Sonarr has for its file. See "Fix the Plex match" below.
- **Refresh the details** asks Plex to read the item's details again. A member's report about wrong details starts it, and checks the match first (`checkMatch`, see below): a refresh can't fix a match to another title, so a match that differs, the episode order, or a match that can't be told goes to the server admin; otherwise the report is fixed once Plex has the request. An admin's run refreshes at once, then hands the report back to them to check the details and mark it fixed.
- When a fix hands a report back, its timeline says why (`TO_ADMIN`), and the admins get the usual Discord alert when the app had started the fix.

### Swap the copy

1. **Wait to start.** It resolves the file again (see "The file a fix acts on") and needs the Plex item's guid. While the title is playing or Radarr or Sonarr is downloading a copy of it, it checks again every 10 minutes, and hands the report back after a day ("It was playing or downloading for a day"). An admin's tap holds only 15 minutes, so their run hands it back then ("It didn't start within 15 minutes of the tap"). When the file changed meanwhile, the copy that was reported is gone, and the report is fixed. A member's swap then checks that the member is still entitled and the title is still in their libraries (SEC-21).
2. **The bad copy** (`lib/problem-reports/bad-copy.ts`): the import in the title's history whose `data.fileId` is the file's id names the download, and the grab with that download id names the release, its info hash and the history record to mark failed. A file added by hand has no grab; its scene name is still passed over.
3. **The gate** records the run with the file's id and the bad release on `PROBLEM_FIX_RUN`, and checks the search cap, the breaker and what let it start (see "Checked again before a grab or a delete").
4. **The interactive search** (`GET /api/v3/release?movieId=` or `?episodeId=` for the file's first episode, two minutes before it times out) asks every indexer.
5. **The pick** (`lib/problem-reports/candidates.ts`, tested on release lists in the shape Radarr and Sonarr answer) takes a release that isn't the bad one by title or info hash; that is unrejected, rejected only by checks starting "Existing file", or held back only for now; that is at least the file's quality, revision and custom format score, so the import is accepted in place; that has the file's languages; and, for Sonarr, that holds exactly the file's episodes, so no season pack and no single episode for a double-episode file. The highest custom format score wins, then quality, then seeders. With none, nothing changes and the report goes back: "The search found no other copy", or "The only other copies are lower quality. Remove the file and search can grab one of them". A dry run stops here, and the report goes to the server admin with the release it would grab.
6. **The grab** passes the second gate (the breaker, and the checks again), then `POST /api/v3/release` with the pick's guid and indexer, while Radarr or Sonarr still hold the search's results (30 minutes).
7. **The wait** checks every 10 minutes for a day, as Look for a better copy does: a new file is the new copy; a stuck or failed download goes back to the server admin, and so does a grab that never shows a download.
8. **The end:** Plex scans the file's folder, the bad copy's grab is marked failed (`POST /api/v3/history/failed/{id}`), so Radarr or Sonarr blocklists its release, and the app checks the blocklist has it. The timeline says which release came in and whether the old one is on the blocklist. Plex is asked for the item again; when the title came back as a new item, the report keeps its new rating key, found by the guid. Marking a grab failed can make Radarr or Sonarr search again ("Redownload failed"); with the new copy in place, that grabs only an upgrade.

A step that runs again after a crash may search again but never grabs twice: a ledger row already marked replaced goes to the wait. The crash may have come before the grab went out, so when the wait's first check, 10 minutes later, finds nothing downloading, the report goes back to the server admin ("The fix was interrupted part way") instead of waiting out the day.

### Remove the file and search

The confirm says the title is unavailable to everyone until a new copy downloads, which release Radarr or Sonarr will blocklist, whether their recycle bin keeps the file, and, when Plex empties its trash after every scan (`autoEmptyTrash`), that the title may come back as a new item without anyone's watched status (`lib/data/problem-removal.ts`, read as the report's page streams).

1. It waits to start, and reads the bad copy, as a swap does.
2. The gate records the run as replacing at once.
3. The bad copy's grab is marked failed first, so the search can't grab the same release again. When that fails, nothing is removed.
4. `DELETE /api/v3/moviefile/{id}` or `/api/v3/episodefile/{id}`. When the delete fails, nothing retries, and the report goes back saying so and that a copy from a download has its release on the blocklist by then. A 409 means the file's root folder is missing.
5. A minute later it monitors the title again (`PUT /api/v3/movie/editor` or `/api/v3/episode/monitor`): with "Unmonitor deleted movies" or "episodes" on, deleting the file unmonitors it a moment later, and an unmonitored title never gets a copy released later. Then `MoviesSearch` or `EpisodeSearch`.
6. It waits as a better copy does, without counting the bad download's failure in the history. A search that finished and grabbed nothing goes back to the server admin: "The file was removed, and the search found nothing to replace it".
7. It ends as a swap does, without marking the grab failed again.

A step that runs again after a crash finds its ledger row and hands the report back without acting ("The fix was interrupted part way"). The file may be deleted already, and a copy that came in since would read as the bad one, so nothing is ever deleted twice; the server admin checks the title and runs the fix again if it's needed.

### Fix the Plex match

Plex matches movies and shows, so a report about an episode matches its show. The check (`lib/problem-reports/match.ts`) compares Plex's match with the title Radarr or Sonarr has for the same file:

1. The file is resolved by the ids Plex holds, as the other fixes resolve it. When that finds the file, Plex and Radarr or Sonarr agree. For an episode, Sonarr's numbers for the file must also include the one Plex shows; when they don't, it's the episode order, which goes to the server admin ("Plex numbers this episode differently from Sonarr").
2. When Plex's ids lead to no title, or to one whose file isn't this one, the title is looked for by folder: the Radarr movie whose file it is (`GET /api/v3/movie`, the whole library), or the Sonarr series whose folder holds it (`GET /api/v3/series`; for a show report, the show's folders). Plex's match then differs, and that title's ids are the ones to match to.
3. Anything else can't be told and goes to the server admin: no Radarr or Sonarr, several versions, a special, a service or Plex that can't be read, or no title that owns the file.

When the match differs, the fix:

1. asks the library section's agent (`GET /library/metadata/<ratingKey>/matches?manual=1` with the section's agent and language) for `tmdb-<id>` for a movie, then its title and year when that finds nothing, or Sonarr's title and year for a show. A result whose legacy guid names the expected id is taken first; otherwise one with the expected title and year, then the first;
2. leaves Plex alone when another item in the section already has that match, since matching would merge the two items ("Another item in the library already has the right match");
3. gates (the hourly cap on Plex changes) and records the run against the old guid, then matches (`PUT /library/metadata/<ratingKey>/match?guid=&name=`), which Plex does in the background;
4. reads the item every 5 seconds for a minute: once it has Radarr's TMDB id (or IMDb id) or Sonarr's TVDB id, the report is fixed. Otherwise the item is matched back to what it had, and the report goes to the server admin; an item that was never matched has nothing to go back to, and the report says to check it in Plex. When the last read fails, Plex is read once more first, so one failed read doesn't undo a match that took. Matching back undoes the run's own change, so it isn't gated or counted against the cap again.

A step that runs again after a crash finds its ledger row: when Plex already has the right title, the match took and the report is fixed; otherwise it goes to the wait without matching again.

### The file a fix acts on

`lib/problem-reports/resolve.ts` finds the file at run time, never from what the report stored, since files change under reports:

1. It reads the Plex item. Versions Plex made with Optimize don't count. A title with more than one real version, or one split into parts, goes to the server admin, since no fix can tell which one the member played.
2. It finds the movie or series by the ids Plex holds (an episode by its show's), never by title.
3. It matches the Plex file to Radarr's file, or one of Sonarr's, by file name and folder name, compared without case: Plex and Radarr or Sonarr often see the same disk under different roots, so whole paths never match. Files that still tie are told apart by size.

Specials (season 0) and anything Radarr or Sonarr doesn't monitor go to the server admin too: Sonarr numbers specials its own way, and an unmonitored title is one the server admin chose to leave alone. The timeline says which case it was.

### Audit

- `PROBLEM_REPORT_CLOSED`: Mark fixed or Close, with the report id, the outcome and whether the member got a note, never a title or a note.
- `PROBLEM_REPORT_SETTINGS_CHANGED`: the switch, members' swaps and their limits: which changed, with the values before and after.
- `PROBLEM_SWAP_APPROVAL_CHANGED`: Swaps need approval, with the member and the new value.
- `PROBLEM_FIX_RUN`: written by the run before it acts, with the report id, the fix, the trigger, who asked and who approved, and the dry-run flag; for a swap or a removal, the file's id and the release it replaces too. Never a title or a note.
- `PROBLEM_BREAKER_RESUMED`: Resume fixes.
- Reading reports is a read of members' content: the list writes `MEMBER_CONTENT_LISTED` and a report writes `MEMBER_CONTENT_VIEWED` for each member whose words it shows, with the surface `problem-reports`, at most once an hour per admin (and member).

The words for a report's status are in `lib/ui/status.ts` (`problemReport`): Sent, Fixing, Fixed, With the server admin, Closed (always with a reason). The problems, their kinds and the words members see are in `lib/problem-reports/taxonomy.ts`; web, Discord and the admin pages read them from there.

## Members' swaps

Members can swap a copy that won't play right, and fix a Plex match, themselves, within limits. It is off until the server admin chooses **Members' swaps** in the settings card (`ProblemReportSettings.automatic`, Off by default), with the limits beside it: **Swaps per member** (3 in any 7 days), **Days between swaps of a title** (14) and **Members' swaps a day** (10, across every member).

- **Off**: reports a swap would fix go to the server admin, as before.
- **Dry run**: a member's report that a swap would fix runs the swap up to its pick, then goes to the server admin with the release it would grab ("Dry run: a swap would bring in Heat.1995.1080p.BluRay-GOOD. Swap the copy to run it"), who runs it in one tap. Nothing changes on its own, and a dry run never counts against anyone's swaps, though its search counts against the day's searches. Members see the server admin's words throughout: the sheet's line and button, and Your reports while the dry run runs. "A different movie or episode plays" checks the match and tells the server admin what it found. Run Dry run for a couple of weeks, reading every "Dry run" step, before choosing On.
- **On**: the sheet offers **Swap the copy** for a problem a swap fixes, and **Fix the details** for "A different movie or episode plays", which runs Fix the Plex match when Radarr or Sonarr has a different title for the file; when the match agrees or can't be told, the report goes to the server admin with what the check found. A swap runs only when the member pressed Swap the copy, so it is never spent without them seeing what it costs.

On needs a recycle bin in each of Radarr and Sonarr that is set up (`recycleBin` in `GET /api/v3/config/mediamanagement`, `lib/problem-reports/recycle-bins.ts`), so the copy a bad swap replaced can be put back. Without one, or when a service can't be read, On stays disabled and the card says which service needs one. Changing the mode records when (`automaticSince`), and a member's swap claimed before that never runs, so switching modes never runs a backlog.

### Which problems a swap fixes

A swap acts on one file: a movie's, with Radarr, or an episode's, with Sonarr. A report about a whole show goes to the server admin (`lib/problem-reports/member-swap-words.ts`).

| Problem | Swaps when |
|---|---|
| Won't start, stops or freezes, glitches, sound out of sync, no sound | the member says other titles play fine on their player, and the copy hasn't played to the end for anyone since it was added. Glitches after a play Plex converted get the playback tips instead |
| Looks filmed off a screen, subtitles stuck on | always: it's in the copy |

A copy that has played to the end goes to the server admin: "It has played to the end since it was added, so it may be your device or connection."

### The limits

`lib/problem-reports/gate.ts` decides from the settings, the member and the ledger alone (`lib/problem-reports/swap-ledger.ts`), so deleting reports never resets a count. The sheet, the report and both gates of the run read the same decision, and the first rule that applies is the one the member reads:

| Rule | Limit | The member reads |
|---|---|---|
| Server-wide | the breaker isn't tripped, and fewer members' swaps than the day's limit began replacing a file in the last 24 hours | "Automatic swaps are paused right now." |
| Approval | Swaps need approval is off for the member | "The server admin checks swaps for your account first." |
| Evidence | Tautulli has the member's play of it in the last 30 days, or they're watching it now | "We can only swap titles you've played recently." |
| Title | no member's swap of it within its cooldown, and fewer than 2 swaps of it from any trigger in 60 days | "This title was swapped recently." |
| Member | fewer swaps than their limit in the last 7 days | "You're out of swaps until Nov 10." |

A refused swap goes to the server admin, with the reason on the timeline. A member's swap counts from its grab for 7 days, unless it ended without a new copy; a title's limits count every attempt but dry runs. The allowance shows only where a swap is spent, while members' swaps are On: "2 of 3 swaps left. One comes back Nov 10.", or with one left, "This is your last swap until Nov 12."

### Checked again before a grab or a delete

A swap's two gates, and a removal's one (see Fixes), check again, in the same serializable transaction that records the run or marks it replacing (`lib/problem-reports/recheck.ts`):

- **A member's swap:** members' swaps are still in the mode it was claimed under and haven't changed since ("Members' swaps were turned off or changed after the member asked, so it didn't run"), and the limits still allow it, its own ledger row left out before the grab. A member's swaps count from their grabs, so when several of their swaps run at once, only as many grab as they have left, and the rest are refused at the gate. Two reports of one title can't both run: a title has one open report, and a fix claims it once.
- **An admin's tap** (Swap the copy or Remove the file and search, on the web or over MCP): the admin is still an admin at each gate, and the run reached its first gate within 15 minutes of the tap, as an admin's confirmation holds in `lib/queue/jobs/member-activity.ts`.

A step that runs again after a crash finds its ledger row first, so neither ever acts twice.

## Rules

`lib/problem-reports/service.ts` is the one entry point for the web and Discord:

- the switch must be on and the member entitled (`full`);
- a report or a follow spends `problem-report:create` (10 an hour) and `problem-report:create:day` (20 a day) per member, before the library check, so a rating key outside the member's libraries still spends one and the check can't be used to probe Plex;
- the title must be in a library shared with the member, checked on the server for every rating key (SEC-21, `lib/problem-reports/access.ts`): admins and the server owner see every library, anyone else needs plex.tv's share list to name the item's section;
- the title's type and details come from Plex, never from the request;
- one open report per title: `ProblemReport.activeKey` holds the title's Plex guid under a unique index until the report closes. A second report of the title joins the open one with an `ALSO_REPORTED` event, written after the failed insert;
- a member's `ALSO_REPORTED` event is written once: the same problem and note again, or a second follow, writes nothing;
- a problem a swap fixes, and a different title playing, are decided when the report is sent, by the rules in Members' swaps; the sheet's offer is only what the member saw;
- following checks the title against the member's libraries too;
- only the reporter can cancel, and only while the report is Sent or With the server admin. Cancelling works with the switch off or a lapsed membership, so a member can always withdraw their own report. Every way of closing a report clears `activeKey`, and closes it for the members who followed it too: they see it as Closed, with "The member who reported it cancelled it".

Each report records the answer to the device question and the evidence from Tautulli (`lib/problem-reports/evidence.ts`) on its `REPORTED` event, or on its `ALSO_REPORTED` event when it joins an open report: the member's last play of the title (the player's name, whether it was converted, when; for a show, its newest episode's), and whether the title has played to the end for anyone since its file was added (never said for a show, which has no file of its own). Tautulli's IP address and device id are never read, so they are never stored. The member's Tautulli `user_id` is their Plex account id. The member waits on these reads, so each is tried once, with a short timeout, and the report is saved without them when Tautulli is slow. The device answer is kept only for the problems that ask it, and only when the evidence names the player of that last play, so a stored answer is about the player the event names. The one exception is a member who starts the title on another player between opening the sheet and sending it: the evidence is read when they send, and then names that player.

Member notes are plain text: format characters (bidi controls, zero-width spaces) are dropped, other control characters become spaces, and they are at most 500 characters (`lib/validations/problem-reports.ts`). Followers see status words only, never who else reported.

## Data

- `ProblemReport`: the reporter, the problem code and note, the title's rating key, guid (`titleKey`) and display fields, `activeKey`, the status, the server admin's notes (one the member sees, one internal), when the admins' Discord alert claimed it (`alertedAt`) and dates.
- `ProblemReport.action` and `runToken`: the fix running or last run, and the fencing token each run bumps.
- `ProblemReportEvent`: the timeline. `REPORTED`, `ALSO_REPORTED` (a follow, or a second member's problem and note), `FIX_STARTED` (the fix and its trigger, and `dryRun` for a dry run), `TO_ADMIN` (why a fix handed it back, or why the app sent a report straight to the server admin; a dry run's names the release it would grab), `FIXED` (by `admin`, or by a `fix`), `CLOSED` (`cancelled` by the reporter, `admin`, or `no_better_copy`), `REOPENED` (the member who reported it asked the server admin after no better copy, or said the new copy is `still_broken`, with their note) and `PLAYS` (they said it plays). `data` is parsed with Zod on read.
- `ProblemFixLedger`: one row per fix run that acted, which the limits read and nothing else writes, with `replacedAt` once the run grabbed or deleted to replace the file, and the title's Plex guid (`titleKey`), by which a title's swaps are counted. Members can't delete it; removing a member sets its person ids to null.
- `User.swapsNeedApproval`: the member's Swaps need approval switch.
- `ProblemReportSettings`: the switch, when the breaker tripped (`breakerTrippedAt`), and members' swaps: the mode (`automatic`), when it last changed (`automaticSince`) and the limits (`weeklySwaps`, `titleCooldownDays`, `dailySwapCap`). One row with id `problem-reports`.

Removing a member deletes their reports, and their `ALSO_REPORTED` events on other members' reports, which hold their notes (`lib/members/erase-problem-reports.ts`, `docs/privacy.md`).

## MCP

The member actions (`reportProblem`, whose `swap` says the member pressed Swap the copy, `followProblemReport`, `cancelProblemReport`, `askServerAdmin`, `answerDoesItPlay` in `actions/problem-reports.ts`) and the admin actions (`resolveProblemReport`, `runProblemFix`, `swapProblemCopy`, `removeProblemFile`, `resumeProblemFixes`, `updateProblemReportSettings`, `setSwapsNeedApproval` in `actions/admin/problem-reports.ts`) are MCP tools like every action. The two fixes that replace the file have their own actions, named so MCP clients see them as destructive (`destructiveHint`); `runProblemFix` refuses them. A fix an MCP client runs is recorded with the trigger `mcp` and goes through the same gate. The member actions' descriptions say that member text is untrusted.

## Testing

The E2E specs sign in as a member who doesn't own the server; the share list comes from the plex.tv mock (`e2e/README.md`, "Library access for a member"). One spec has the admin close a report with a note and the member read it on `/report`. `e2e/problem-reports-missing.spec.ts` reports missing episodes against the Sonarr mock (`e2e/mocks/sonarr-server.ts`): the answers for an episode that hasn't aired and a season that isn't monitored, a member's report starting Look for the episodes, and an admin starting it from a report. `e2e/problem-reports-better-copy.spec.ts` reports a blurry movie against the Radarr mock (`e2e/mocks/radarr-server.ts`): a copy below the cutoff starting Look for a better copy, one at the cutoff answered as the best copy and sent to the server admin anyway, and an admin starting it from a report. `e2e/problem-reports-swap.spec.ts` has the admin swap a copy that won't start, against the same mock, until the report is fixed with the old release blocklisted, and remove the file behind its confirm until Radarr searches again. `e2e/problem-reports-member-swap.spec.ts` covers members' swaps against the same mock: the admin turning them On once Radarr keeps a recycle bin, a member watching a copy that looks filmed off a screen swapping it (the run waits until the stub Plex server lists no stream of it) and then saying the new copy is still broken, a dry run that stops at its pick while the member sees the report with the server admin, and a member out of swaps. A fix's next step waits in the job queue, so these specs promote the delayed job instead of waiting for it.
